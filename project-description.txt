8. Technical Requirements (deltas) Frontend (both): mobile-first reporting flow completable in under 60
seconds; camera capture; location picker on a campus map; public board with infinite scroll. Backend (both): match
suggestions generated on report creation and refreshed nightly; private fields stored encrypted and never included
in any public response – enforce this structurally, not by remembering to omit them. Data model
(both): Item, ItemCategory, Location, PrivateDetail (encrypted), MatchSuggestion, Claim, VerificationChallenge,
CustodyRecord, Handover, DisposalRecord, AuditEntry. API (both): /items, /items/:id/matches, /claims,
/claims/:id/verify, /handovers, /board (public, redacted). Security (both): the public board endpoint must
be covered by an explicit test asserting that no private field ever appears in its response, for every item state.
TRACK J · Node.js + MongoDB. Enforce redaction in a serialisation layer – a dedicated public DTO that the
private fields cannot reach.
9. Admin Dashboard Item inventory by custody location · pending claims and verification queue · match
review · ageing and disposal queue · category and retention configuration · return-rate reporting.
10. Reporting & Analytics Items reported against returned, giving the return rate · median time to return ·
loss hotspots by campus location and time · category distribution · unclaimed volume and disposal · verification
failure rate, which is a signal for false claims.
11. Notifications & Communication Possible match found for your lost item · claim submitted on your found
item · verification required · handover scheduled · unclaimed item ageing warning.
12. Third-Party Integrations ERP and SSO for identity, object storage for images, email and SMS, optionally
campus CCTV location reference – metadata only, no video.
